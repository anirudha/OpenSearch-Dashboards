Design Documents

Architecture decisions, RFCs, and design rationale for Dashboards-as-Code.

OpenAPI Client Generation & Schema Mapping Active

Problem

The DaC CLI (osdctl) has a hand-written HTTP client. Each new API endpoint requires manual client code. Meanwhile, the saved object schemas (dashboard, visualization, index-pattern, search) are JSON Schema files that aren't connected to the OpenAPI spec. This creates two maintenance burdens and no generated client libraries for other languages.

Solution: Two Schemas, One Pipeline

Use the existing OpenAPI spec as the single source of truth for API shape, and the existing saved object JSON Schemas as the single source of truth for resource attributes. Connect them to auto-generate typed clients.

What Changes

1. Enriched OpenAPI Spec with Typed Attributes

Today attributes is type: object (untyped). We replace it with $ref to the saved object schemas:


# Before
attributes:
  type: object
  description: The metadata of the saved object

# After - per-type request schemas
DashboardCreateRequest:
  type: object
  required: [attributes]
  properties:
    attributes:
      $ref: 'dashboard.v1.schema.json'
    references:
      $ref: '#/components/schemas/References'

2. DaC Endpoints Added to OpenAPI Spec

3. Generated TypeScript Client


# Generate types from OpenAPI spec
npx openapi-typescript docs/openapi/saved_objects/saved_objects.yml \
  -o packages/osd-dashboards-sdk/src/generated/api.d.ts

The generated types replace the manual OsdClient interfaces. The SDK builder pattern stays as the ergonomic authoring layer on top of generated types.

4. Multi-Language Client Generation (Future)


# Python
openapi-generator generate -i saved_objects.yml -g python -o clients/python/

# Go
openapi-generator generate -i saved_objects.yml -g go -o clients/go/

# Java
openapi-generator generate -i saved_objects.yml -g java -o clients/java/

Architecture


 User Code (TS / Python / Go / Java)
         |  uses generated client
         v
 Generated API Client    <-- from OpenAPI spec (routes + typed attributes)
         |  HTTP
         v
 OSD Server API
 Routes validate attributes against JSON Schemas at runtime
         |
         v
 Saved Objects (OpenSearch index)

Key insight: The OpenAPI spec defines the API contract (endpoints, auth, pagination). The saved object JSON Schemas define the domain model (what a dashboard looks like). By $ref-ing the JSON Schemas from within the OpenAPI spec, generated clients get both — typed API calls with typed resource attributes.

What This Does NOT Change

  • Saved object storage format — still JSON in OpenSearch indices
  • NDJSON import/export — still supported, the OpenAPI spec documents it
  • SDK builder pattern — stays as the ergonomic authoring layer on top of generated types
  • Internal schema model — no Perses adoption; we use our own JSON Schemas

Relationship to Other Efforts

  • Issue #6719 (Standardize OSD APIs with OpenAPI): This is a concrete implementation scoped to saved objects. The pattern extends to other OSD APIs.
  • Perses compatibility: If needed later, a mapping layer can translate between OSD saved objects and Perses format. See the RFC below.

Perses Schema Compatibility Layer Future / On-demand

Context

Perses is a CNCF sandbox project defining a vendor-neutral, Kubernetes-style resource model for observability dashboards. It's adopted by Red Hat, SAP, and Amadeus, and has a Grafana migration tool.

Our position: OpenSearch Dashboards saved objects are a 10+ year proven schema inherited from Kibana. We do not replace them. Instead, we offer an optional bidirectional translation layer that maps between OSD saved objects and Perses format — driven by customer requests, not speculative adoption.

Translation Model

Grafana Migration Path

Perses maintains a Grafana migration tool. Combined with this layer:


Grafana Dashboard --> (Perses migrator) --> Perses Format --> (this layer) --> OSD Saved Objects

Two-hop migration from Grafana without maintaining a direct Grafana importer.

CLI Integration (Planned)


# Import Perses dashboard into OSD project
osdctl import --from perses --file grafana-migrated.yaml --output ./dashboards/

# Export OSD dashboard to Perses format
osdctl export --to perses --type dashboard --id abc-123 --output ./perses/

# Bulk convert a directory
osdctl convert --from perses --to osd --dir ./perses-dashboards/ --output ./osd-dashboards/

When to Build This

This RFC is parked until customer demand materializes. Triggers:

  1. Multiple customer requests for Grafana → OSD migration
  2. Perses reaches CNCF incubation (signals real standardization momentum)
  3. A concrete deployment where Perses + OSD coexist and need interop

Until then, the saved object schema + OpenAPI client generation is the priority.
