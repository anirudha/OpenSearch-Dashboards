CLI Reference: osdctl

osdctl is the command-line tool for Dashboards-as-Code workflows. It orchestrates building, validating, diffing, deploying, and pulling OpenSearch Dashboards resources.

Installation


# Via npm (recommended)
npm install -g @osd/cli

# Via Homebrew (macOS/Linux)
brew install opensearch-project/tap/osdctl

# Via Docker
docker pull opensearchproject/osdctl:latest
docker run --rm opensearchproject/osdctl osdctl --version

# Verify
osdctl --version

Configuration

Config File Location

osdctl reads configuration from two locations (merged, project config takes precedence):

  1. User-level: ~/.osdctl/config.yaml
  2. Project-level: .osdctl.yaml in the current directory (or nearest parent)

Config File Format


# Default profile to use when --profile is not specified
defaultProfile: dev

# Default output directory for build artifacts
outputDir: ./built

# Connection profiles for different environments
profiles:
  dev:
    url: http://localhost:5601
    auth:
      type: basic
      username: admin
      # Password read from OSD_PASSWORD env var
  staging:
    url: https://dashboards-staging.internal:5601
    auth:
      type: basic
      username: deployer
  prod:
    url: https://dashboards.company.com:5601
    auth:
      type: saml
      token_command: "aws sso get-role-credentials --role-name DashboardAdmin --account-id 123456 --output text --query roleCredentials.accessKeyId"
    variables:
      cluster_name: prod-cluster
      env_label: production

# Global variables (available to all profiles)
variables:
  team: platform
  region: us-east-1

# Lint rules
lint:
  require-labels:
    - env
    - team
  require-annotations:
    - owner
  require-description: warn
  max-panels: 50
  naming-convention: kebab-case
  allowed-data-sources:
    - "metrics-*"
    - "logs-*"

Authentication

Credentials are resolved in this order:

  1. Environment variables (highest priority):
  2. OSD_URL -- Override the profile URL
  3. OSD_TOKEN -- Bearer token authentication
  4. OSD_USERNAME -- Basic auth username
  5. OSD_PASSWORD -- Basic auth password
  6. Profile config -- auth section in the profile
  7. Interactive prompt -- If a password is required but not found, osdctl prompts interactively

Supported authentication types:

TypeConfigDescription
basictype: basic, usernameUsername/password. Password from OSD_PASSWORD env var.
tokentype: tokenBearer token. Token from OSD_TOKEN env var.
samltype: saml, token_commandExecutes the token_command to obtain a token dynamically.

token_command details:

The token_command option executes a shell command to obtain a bearer token dynamically. This is useful for OIDC/SAML providers like AWS SSO, Okta, or Azure AD:


profiles:
  prod:
    url: https://dashboards.company.com:5601
    auth:
      type: saml
      token_command: "aws sso get-role-credentials --role-name DashboardAdmin --account-id 123456 --output text --query roleCredentials.accessKeyId"
  • The command is executed with a 10-second timeout to prevent hangs.
  • The token is cached for the duration of the CLI session (no re-execution per request).
  • The command's stdout is trimmed and used as the Authorization: Bearer <token> header.
  • Auth priority: OSD_TOKEN env var > token in config > token_command > username/password.

Security note: Credentials are never stored in config files. Always use environment variables, keychains, or token_command for credential retrieval.

HTTP timeout: The CLI client uses a 30-second HTTP timeout for all requests to the OpenSearch Dashboards server. If a request exceeds this limit (e.g., a large _bulk_apply), the CLI will report a timeout error.

Variables

Variables allow you to parameterize dashboard definitions with values that differ per environment. They are substituted during build and apply.

Syntax:

  • ${var.NAME} -- Resolved from the variables section in config (profile-level overrides global)
  • ${env.NAME} -- Resolved from environment variables

Config example:


# Global variables
variables:
  team: platform
  region: us-east-1

profiles:
  dev:
    url: http://localhost:5601
    variables:
      cluster_name: dev-cluster
  prod:
    url: https://dashboards.company.com:5601
    variables:
      cluster_name: prod-cluster

Usage in dashboard source:


const dashboard = Dashboard.create('monitoring')
  .title('${var.cluster_name} Monitoring')
  .labels({ team: '${var.team}', region: '${var.region}' });

After building with --profile prod, the title becomes prod-cluster Monitoring.

Variables are also substituted when running osdctl apply, so you can use them directly in YAML definition files:


spec:
  title: "${var.cluster_name} Monitoring"
  labels:
    env: "${env.DEPLOY_ENV}"

Commands

osdctl init

Scaffold a new Dashboards-as-Code project with SDK dependencies, folder structure, example dashboards, and CI configuration. The generated example files use SDK builder code (not raw JSON), giving you a working starting point with the fluent TypeScript API.

Usage:


osdctl init [directory] [options]

Arguments:

ArgumentDescription
directoryTarget directory name. Created if it does not exist. Defaults to . (current directory).

Flags:

FlagShortDefaultDescription
--language-ltypescriptSDK language. Supported: typescript. Coming soon: python, go, java.

Examples:


# Create a TypeScript project
osdctl init --language typescript my-dashboards

# Create in the current directory
osdctl init .

# Shorthand
osdctl init -l typescript my-project

Generated structure:


my-dashboards/
  package.json            # npm project with build/validate/apply scripts
  tsconfig.json           # TypeScript configuration
  .osdctl.yaml            # CLI config with dev/staging/prod profiles
  .gitignore              # Ignores built/, node_modules/
  src/
    dashboards/
      example.ts          # Example dashboard using SDK builders
  built/                  # Build output directory

osdctl build

Compile SDK source files (TypeScript) into JSON or YAML dashboard definitions.

Usage:


osdctl build [options]

Flags:

FlagShortDefaultDescription
-fBuild a single source file
-dBuild all source files in a directory
-oyamlOutput format: json or yaml
--output-dir./builtDirectory for built output files
--stdoutfalsePrint output to stdout instead of writing files

Examples:


# Build a single file to YAML
osdctl build -f src/dashboards/cpu-monitoring.ts

# Build a single file to JSON
osdctl build -f src/dashboards/cpu-monitoring.ts -o json

# Build all files in a directory
osdctl build -d src/dashboards/

# Build to a custom output directory
osdctl build -d src/dashboards/ --output-dir ./dist

# Preview output without writing files
osdctl build -f src/dashboards/cpu-monitoring.ts --stdout

# Build using npm script (configured by init)
npm run build

How it works:

  1. Detects the language from the file extension or project config.
  2. Executes the source file (e.g., via npx tsx for TypeScript).
  3. Captures the SDK output (JSON/YAML files written by toJSON()/toYAML() calls).
  4. Writes results to the output directory (one file per dashboard).

osdctl validate

Validate dashboard definitions against the JSON Schema.

Usage:


osdctl validate [options]

Flags:

FlagDefaultDescription
--input-dir./builtDirectory containing dashboard definitions to validate
--serverfalseEnable server-side validation (checks data sources, plugins, index patterns)
--profiledefault profileConnection profile for server-side validation

Examples:


# Local-only validation (no server needed)
osdctl validate

# Validate a specific directory
osdctl validate --input-dir ./dist

# Server-side validation (full checks)
osdctl validate --server --profile staging

osdctl diff

Compare local dashboard definitions against the deployed state on a running OpenSearch Dashboards instance.

Usage:


osdctl diff [options]

Flags:

FlagShortDefaultDescription
--input-dir./builtDirectory containing local definitions
--output-dirWrite .diff files to this directory
--output-otextOutput format: text (human-readable) or json (machine-readable)
--profiledefault profileConnection profile

Examples:


# Diff against dev
osdctl diff --profile dev

# Diff against production
osdctl diff --profile prod

# Save diff output to files
osdctl diff --profile prod --output-dir ./diffs

Output:


Comparing 5 dashboards against prod...

  cpu-monitoring               UPDATED
    ~ title: "CPU Metrics" -> "CPU Monitoring"
    + panels[3]: new panel "cpu-p99-latency"

  memory-overview              UNCHANGED
  disk-usage                   NEW
  network-traffic              UPDATED
    ~ refreshInterval: "1m" -> "30s"
  application-errors           UNCHANGED

2 updated, 1 new, 2 unchanged

Status values:

StatusMeaning
NEWDashboard does not exist on the server
UPDATEDDashboard exists but has differences
UNCHANGEDDashboard is identical to the deployed version
ERRORCould not compare (e.g., permission denied)

Exit codes:

CodeMeaning
0No drift detected -- all resources match the deployed state
1Error -- could not complete the diff (e.g., connection failure)
2Drift detected -- one or more resources differ from the deployed state

These exit codes are designed for CI/CD pipelines where you need to distinguish between "no changes" and "changes detected" without parsing text output.

JSON output mode:


# Machine-readable output for CI scripts
osdctl diff --profile prod --output json

Returns a JSON array of diff results, suitable for programmatic processing:


[
  { "type": "dashboard", "id": "cpu-monitoring", "status": "updated", "diff": [...] },
  { "type": "dashboard", "id": "memory-overview", "status": "unchanged", "diff": [] }
]

How it works: For each local definition, osdctl diff calls POST /api/saved_objects/_diff on the server, which performs a structured comparison and returns the specific fields that changed.

osdctl apply

Deploy dashboard definitions to a running OpenSearch Dashboards instance.

Usage:


osdctl apply [options]

Flags:

FlagDefaultDescription
--input-dir./builtDirectory containing definitions to deploy
--dry-runfalsePreview changes without applying
--confirmfalsePrompt for confirmation before applying
--profiledefault profileConnection profile

Examples:


# Dry-run: see what would change
osdctl apply --dry-run --profile prod

# Apply to development
osdctl apply --profile dev

# Apply to production with confirmation
osdctl apply --profile prod --confirm

# Apply using environment variables (useful in CI)
OSD_URL=https://dashboards.company.com OSD_TOKEN=$TOKEN osdctl apply

Output:


Applying 5 dashboards to prod...
  cpu-monitoring               UPDATED  (v5 -> v6)
  memory-overview              UNCHANGED
  disk-usage                   CREATED  (v1)
  network-traffic              UPDATED  (v3 -> v4)
  application-errors           UNCHANGED

3 changes applied, 2 unchanged

How it works:

  1. Reads all definitions from the input directory.
  2. Calls POST /api/saved_objects/_bulk_apply with all resources.
  3. Uses optimistic concurrency (If-Match header) to prevent overwriting concurrent changes.
  4. Automatically stamps managed-by: osdctl label and last-applied-hash annotation on all applied objects.
  5. Reports per-resource status: CREATED, UPDATED, UNCHANGED, or ERROR.

Dry-run mode (--dry-run): Sends the request with dryRun: true. The server validates all resources and reports what would change without persisting anything. If any resource fails validation, the entire batch is rejected.

osdctl pull

Export dashboards from a running instance to local files.

Usage:


osdctl pull [options]

Flags:

FlagShortDefaultDescription
--output-dir./pulledDirectory to write pulled definitions
-oyamlOutput format: json or yaml
--labelFilter by labels (format: key=value,key2=value2)
--per-page100Number of objects per page when fetching from the server
--profiledefault profileConnection profile

Examples:


# Pull all dashboards from production
osdctl pull --profile prod

# Pull as JSON
osdctl pull --profile prod -o json

# Pull only dashboards for a specific team
osdctl pull --profile prod --label team=platform

# Pull only dashboards managed by osdctl
osdctl pull --profile prod --label managed-by=osdctl

# Pull to a specific directory
osdctl pull --profile prod --output-dir ./exported

Output:


Pulling dashboards from prod...
  Wrote pulled/cpu-monitoring.yaml
  Wrote pulled/memory-overview.yaml
  Wrote pulled/disk-usage.yaml
  Wrote pulled/network-traffic.yaml

4 dashboards pulled

How it works:

  1. Calls GET /api/saved_objects/_export_clean to retrieve dashboards in the clean, deterministic format.
  2. Writes one file per dashboard.
  3. Label filtering uses the server-side _find endpoint with label query parameters.

osdctl lint

Check dashboard definitions against organizational policies and best practices.

Usage:


osdctl lint [options]

Flags:

FlagDefaultDescription
--input-dir./builtDirectory containing definitions to lint

Examples:


# Lint all built dashboards
osdctl lint

# Lint a specific directory
osdctl lint --input-dir ./pulled

Output:


Linting 5 dashboards...
  cpu-monitoring.yaml
    WARN  no "owner" annotation set
    WARN  no description provided
  disk-usage.yaml
    ERROR missing required label "env"
  memory-overview.yaml         OK
  network-traffic.yaml         OK
  application-errors.yaml      OK

2 warnings, 1 error

Lint rules are configured in .osdctl.yaml:


lint:
  # Require these labels on all dashboards
  require-labels:
    - env
    - team

  # Require these annotations
  require-annotations:
    - owner

  # Require a non-empty description (warn or error)
  require-description: warn

  # Maximum panels per dashboard
  max-panels: 30

  # Dashboard name format (kebab-case, snake_case, or camelCase)
  naming-convention: kebab-case

  # Allowed data source name patterns
  allowed-data-sources:
    - "metrics-*"
    - "logs-*"
    - "traces-*"

Built-in rules:

RuleSeverityDescription
require-labelserrorSpecified labels must be present
require-annotationserrorSpecified annotations must be present
require-descriptionconfigurableDashboard must have a non-empty description
max-panelserrorDashboard must not exceed the panel limit
naming-conventionerrorDashboard name must match the pattern
allowed-data-sourceserrorData source names must match allowed patterns
no-duplicate-panel-nameserrorPanel names must be unique within a dashboard
valid-grid-positionserrorPanel positions must not overlap or exceed grid bounds

Multi-Environment Workflow

A typical DaC workflow promotes dashboards across environments using profiles.

Development


# Build and deploy to dev frequently
osdctl build -d src/dashboards/
osdctl apply --profile dev

Staging (from CI on PR merge to a staging branch)


osdctl build -d src/dashboards/
osdctl validate --server --profile staging
osdctl diff --profile staging
osdctl apply --profile staging

Production (from CI on merge to main)


osdctl build -d src/dashboards/
osdctl validate --server --profile prod
osdctl diff --profile prod
osdctl apply --profile prod --confirm

See the CI/CD Integration Guide for complete pipeline configurations.
