Cookbook: Common Patterns

This cookbook provides reusable patterns for common Dashboards-as-Code scenarios. Each pattern includes a complete code example and explanation.

Pattern: Generating Dashboards Per-Service from a List

When you have many services that all need the same standard monitoring dashboard, generate them programmatically rather than writing each one by hand.


// src/dashboards/per-service.ts
import { Dashboard, Panel, Query, DataSource } from '@opensearch-dashboards/sdk';

interface ServiceConfig {
  name: string;
  team: string;
  index: string;
  owner: string;
}

const services: ServiceConfig[] = [
  { name: 'payment-api', team: 'payments', index: 'logs-payment', owner: 'payments@company.com' },
  { name: 'user-service', team: 'identity', index: 'logs-user', owner: 'identity@company.com' },
  { name: 'order-service', team: 'commerce', index: 'logs-order', owner: 'commerce@company.com' },
  { name: 'notification-api', team: 'platform', index: 'logs-notify', owner: 'platform@company.com' },
  { name: 'search-service', team: 'search', index: 'logs-search', owner: 'search@company.com' },
];

for (const svc of services) {
  Dashboard.create(`${svc.name}-monitoring`)
    .title(`${svc.name} Monitoring`)
    .description(`Standard monitoring dashboard for ${svc.name}`)
    .labels({ env: 'production', team: svc.team, service: svc.name })
    .annotation('owner', svc.owner)
    .annotation('generated', 'true')
    .timeRange('now-1h', 'now')
    .refreshInterval('30s')
    .addPanel(
      Panel.create('request-rate')
        .visualization('line')
        .gridPosition({ x: 0, y: 0, w: 24, h: 10 })
        .query(Query.ppl(`source = ${svc.index} | stats count() as requests by span(timestamp, 1m)`))
        .option('showLegend', true)
    )
    .addPanel(
      Panel.create('error-rate')
        .visualization('line')
        .gridPosition({ x: 24, y: 0, w: 24, h: 10 })
        .query(Query.ppl(`source = ${svc.index} | where level = 'ERROR' | stats count() as errors by span(timestamp, 1m)`))
        .option('showLegend', true)
    )
    .addPanel(
      Panel.create('p95-latency')
        .visualization('line')
        .gridPosition({ x: 0, y: 10, w: 24, h: 10 })
        .query(Query.ppl(`source = ${svc.index} | stats percentile(latency_ms, 95) as p95 by span(timestamp, 1m)`))
    )
    .addPanel(
      Panel.create('recent-errors')
        .visualization('table')
        .gridPosition({ x: 24, y: 10, w: 24, h: 10 })
        .query(Query.ppl(`source = ${svc.index} | where level = 'ERROR' | sort - timestamp | fields timestamp, message, trace_id | head 20`))
    )
    .addDataSource(DataSource.create(`${svc.name}-logs`).type('opensearch').default(true))
    .toYAML(`built/${svc.name}-monitoring.yaml`);
}

Running osdctl build -f src/dashboards/per-service.ts produces 5 dashboard files, one per service, all following the same layout but with service-specific data sources and queries.

To add a new service, add an entry to the services array and rebuild.

Pattern: Shared Panel Library Across Teams

Create a centralized library of standard panels that multiple teams import and reuse.

Define the Library


// shared/panels/standard.ts
import { Panel, Query } from '@opensearch-dashboards/sdk';

/**
 * Standard request rate panel (line chart).
 */
export function requestRatePanel(name: string, index: string): Panel {
  return Panel.create(name)
    .visualization('line')
    .gridPosition({ x: 0, y: 0, w: 24, h: 10 })
    .query(Query.ppl(`source = ${index} | stats count() as requests by span(timestamp, 1m)`))
    .option('showLegend', true)
    .option('yAxisLabel', 'Requests/min');
}

/**
 * Standard error rate panel (area chart).
 */
export function errorRatePanel(name: string, index: string): Panel {
  return Panel.create(name)
    .visualization('area')
    .gridPosition({ x: 0, y: 0, w: 24, h: 10 })
    .query(Query.ppl(`source = ${index} | where status >= 500 | stats count() as errors by span(timestamp, 1m)`))
    .option('showLegend', true)
    .option('yAxisLabel', 'Errors/min');
}

/**
 * Standard latency percentiles panel (line chart with p50, p95, p99).
 */
export function latencyPercentilesPanel(name: string, index: string): Panel {
  return Panel.create(name)
    .visualization('line')
    .gridPosition({ x: 0, y: 0, w: 24, h: 10 })
    .query(Query.ppl(
      `source = ${index} | stats ` +
      `percentile(latency_ms, 50) as p50, ` +
      `percentile(latency_ms, 95) as p95, ` +
      `percentile(latency_ms, 99) as p99 ` +
      `by span(timestamp, 1m)`
    ))
    .option('showLegend', true)
    .option('yAxisLabel', 'Latency (ms)');
}

/**
 * Standard health check metric (gauge).
 */
export function healthGauge(name: string, index: string): Panel {
  return Panel.create(name)
    .visualization('gauge')
    .gridPosition({ x: 0, y: 0, w: 8, h: 8 })
    .query(Query.ppl(`source = ${index} | where status < 500 | stats count() as ok | eval health = ok * 100 / (ok + 1)`))
    .option('min', 0)
    .option('max', 100)
    .option('thresholds', [
      { value: 0, color: 'red' },
      { value: 90, color: 'yellow' },
      { value: 99, color: 'green' },
    ]);
}

/**
 * Markdown header panel for section breaks.
 */
export function sectionHeader(name: string, title: string, subtitle?: string): Panel {
  const content = subtitle ? `## ${title}\n${subtitle}` : `## ${title}`;
  return Panel.create(name)
    .visualization('markdown')
    .gridPosition({ x: 0, y: 0, w: 48, h: 3 })
    .option('content', content);
}

Use the Library


// src/dashboards/payment-api.ts
import { Dashboard, DataSource } from '@opensearch-dashboards/sdk';
import {
  sectionHeader,
  requestRatePanel,
  errorRatePanel,
  latencyPercentilesPanel,
  healthGauge,
} from '../../shared/panels/standard';

const INDEX = 'logs-payment-api';

Dashboard.create('payment-api-overview')
  .title('Payment API Overview')
  .description('Standard operational dashboard for the Payment API service')
  .labels({ env: 'production', team: 'payments', service: 'payment-api' })
  .annotation('owner', 'payments@company.com')
  .timeRange('now-1h', 'now')
  .refreshInterval('30s')
  // Header row
  .addPanel(sectionHeader('header', 'Payment API', 'Real-time operational metrics'))
  // Health gauge
  .addPanel(healthGauge('health', INDEX))
  // Traffic section
  .addPanel(requestRatePanel('request-rate', INDEX))
  .addPanel(errorRatePanel('error-rate', INDEX))
  // Latency section
  .addPanel(latencyPercentilesPanel('latency', INDEX))
  .addDataSource(DataSource.create('payment-logs').type('opensearch').default(true))
  .toYAML('built/payment-api-overview.yaml');

This pattern ensures consistency across all teams while allowing customization where needed.

Pattern: Environment-Specific Overrides

Different environments often require different data sources, time ranges, or thresholds. Use environment variables or configuration objects to parameterize dashboards.

Using Environment Variables


// src/dashboards/cpu-monitoring.ts
import { Dashboard, Panel, Query, DataSource } from '@opensearch-dashboards/sdk';

const ENV = process.env.DEPLOY_ENV || 'dev';

// Environment-specific configuration
const envConfig: Record<string, {
  dataSource: string;
  refreshInterval: string;
  timeRange: { from: string; to: string };
  alertThreshold: number;
}> = {
  dev: {
    dataSource: 'dev-metrics',
    refreshInterval: '10s',
    timeRange: { from: 'now-30m', to: 'now' },
    alertThreshold: 95,
  },
  staging: {
    dataSource: 'staging-metrics',
    refreshInterval: '30s',
    timeRange: { from: 'now-1h', to: 'now' },
    alertThreshold: 90,
  },
  prod: {
    dataSource: 'prod-metrics-cluster',
    refreshInterval: '1m',
    timeRange: { from: 'now-6h', to: 'now' },
    alertThreshold: 80,
  },
};

const config = envConfig[ENV];
if (!config) {
  throw new Error(`Unknown environment: ${ENV}. Valid: ${Object.keys(envConfig).join(', ')}`);
}

Dashboard.create('cpu-monitoring')
  .title(`CPU Monitoring (${ENV})`)
  .description(`CPU metrics for the ${ENV} environment`)
  .labels({ env: ENV, team: 'platform' })
  .timeRange(config.timeRange.from, config.timeRange.to)
  .refreshInterval(config.refreshInterval)
  .addPanel(
    Panel.create('cpu-usage')
      .visualization('gauge')
      .gridPosition({ x: 0, y: 0, w: 12, h: 8 })
      .query(Query.ppl("source = metrics | stats avg(cpu_percent) as usage"))
      .option('min', 0)
      .option('max', 100)
      .option('thresholds', [
        { value: 0, color: 'green' },
        { value: config.alertThreshold, color: 'red' },
      ])
  )
  .addDataSource(DataSource.create(config.dataSource).type('opensearch').default(true))
  .toYAML('built/cpu-monitoring.yaml');

Build for each environment in CI:


DEPLOY_ENV=staging osdctl build -f src/dashboards/cpu-monitoring.ts
osdctl apply --profile staging

DEPLOY_ENV=prod osdctl build -f src/dashboards/cpu-monitoring.ts
osdctl apply --profile prod

Pattern: Dashboard Versioning and Rollback

Since all dashboard definitions are in Git, versioning and rollback are handled through standard Git operations.

Tag Releases


# After validating a set of dashboard changes
git tag -a dashboards-v1.5.0 -m "Add latency percentile panels to all service dashboards"
git push origin dashboards-v1.5.0

Rollback to a Previous Version


# Check out the previous tag
git checkout dashboards-v1.4.0

# Rebuild and deploy
osdctl build -d src/dashboards/ -o yaml
osdctl apply --profile prod

# Return to main
git checkout main

Rollback a Single Dashboard


# Find when the dashboard was last known-good
git log --oneline -- src/dashboards/cpu-monitoring.ts

# Check out that specific file from a previous commit
git checkout abc123 -- src/dashboards/cpu-monitoring.ts

# Build and deploy
osdctl build -f src/dashboards/cpu-monitoring.ts
osdctl apply --profile prod

# Commit the rollback
git add src/dashboards/cpu-monitoring.ts
git commit -m "Rollback cpu-monitoring to known-good state"

Pattern: Validating Dashboards in a Pre-Commit Hook

Catch validation errors before they are committed using a Git pre-commit hook.

Using a Shell Script


#!/usr/bin/env bash
# .git/hooks/pre-commit (make executable: chmod +x .git/hooks/pre-commit)
set -euo pipefail

# Check if any dashboard files are staged
STAGED_DASHBOARDS=$(git diff --cached --name-only --diff-filter=ACM -- 'src/dashboards/*.ts' 'src/dashboards/*.json' 'src/dashboards/*.yaml')

if [ -z "$STAGED_DASHBOARDS" ]; then
  exit 0
fi

echo "Dashboard files staged for commit. Running validation..."

# Build staged dashboard files
for file in $STAGED_DASHBOARDS; do
  if [[ "$file" == *.ts ]]; then
    osdctl build -f "$file" -o yaml 2>&1 || {
      echo "BUILD FAILED: $file"
      exit 1
    }
  fi
done

# Validate built output
osdctl validate --input-dir ./built 2>&1 || {
  echo "VALIDATION FAILED"
  exit 1
}

# Lint
osdctl lint --input-dir ./built 2>&1 || {
  echo "LINT FAILED"
  exit 1
}

echo "All dashboard validations passed."

Using Husky (npm-based projects)

Install husky:


npm install --save-dev husky
npx husky init

Create the hook:


# .husky/pre-commit
osdctl build -d src/dashboards/ -o yaml
osdctl validate --input-dir ./built
osdctl lint --input-dir ./built

Add to package.json:


{
  "scripts": {
    "prepare": "husky"
  }
}

Pattern: Multi-Tenant Dashboards with Workspace Support

OpenSearch Dashboards supports workspaces (multi-tenancy). When managing dashboards across workspaces, organize your code by workspace.

Directory Structure


src/
  dashboards/
    global/                    # Dashboards available in all workspaces
      system-health.ts
    workspace-analytics/       # Analytics team workspace
      user-analytics.ts
      conversion-funnel.ts
    workspace-security/        # Security team workspace
      security-overview.ts
      threat-detection.ts

Workspace-Aware Build and Deploy


// src/dashboards/workspace-analytics/user-analytics.ts
import { Dashboard, Panel, Query, DataSource } from '@opensearch-dashboards/sdk';

Dashboard.create('user-analytics')
  .title('User Analytics')
  .description('User engagement and retention metrics')
  .labels({
    env: 'production',
    team: 'analytics',
    workspace: 'analytics',  // Label for workspace association
  })
  .annotation('workspace', 'analytics')
  // ... panels and data sources
  .toYAML('built/workspace-analytics/user-analytics.yaml');

Deploy per workspace:


# Deploy global dashboards
osdctl apply --input-dir ./built/global --profile prod

# Deploy analytics workspace dashboards
osdctl apply --input-dir ./built/workspace-analytics --profile prod

# Deploy security workspace dashboards
osdctl apply --input-dir ./built/workspace-security --profile prod

Anti-Patterns to Avoid

1. Committing built output to Git

Problem: Committing the built/ directory creates merge conflicts, duplicates source of truth, and bloats the repository.

Solution: Add built/ to .gitignore. Build artifacts are generated in CI from the source files.


# .gitignore
built/

2. Hardcoding environment-specific values

Problem: Putting production URLs, credentials, or data source names directly in dashboard code makes it impossible to promote across environments.

Solution: Use environment variables or configuration objects for anything that varies between environments. See the environment-specific overrides pattern above.

3. One giant file for all dashboards

Problem: Putting all dashboard definitions in a single file makes it hard to review changes, causes merge conflicts, and slows builds.

Solution: One file per dashboard (or per logical group of related dashboards). The per-service generation pattern is an exception where a single file produces multiple dashboards.

4. Manual UI edits to code-managed dashboards

Problem: Editing a code-managed dashboard through the UI creates drift. The next osdctl apply will overwrite the manual change.

Solution: Always make changes through the code workflow. For emergencies, make the UI edit, then immediately pull the change into code:


osdctl pull --profile prod --label managed-by=osdctl -o yaml
# Diff against your source, incorporate changes, commit

5. Skipping validation in CI

Problem: Deploying without validation can push broken dashboards to production.

Solution: Always run osdctl validate and osdctl lint as mandatory CI steps. Fail the pipeline on errors.

6. Using auto-generated panel names

Problem: Panel names like panel-1, panel-2 are meaningless and make diffs hard to understand.

Solution: Use descriptive, stable names: cpu-usage-over-time, error-rate-by-endpoint, top-slow-queries.

7. Not setting labels

Problem: Without labels, you cannot filter, organize, or audit dashboards at scale. You cannot determine which team owns a dashboard or which environment it belongs to.

Solution: Always set at minimum env and team labels. Configure lint rules to enforce this:


# .osdctl.yaml
lint:
  require-labels:
    - env
    - team

8. Deploying directly from a developer workstation

Problem: Deploying from a local machine bypasses code review, validation, and audit trails.

Solution: Deploy through CI/CD pipelines only. Use osdctl apply --dry-run locally for testing, and let the pipeline handle actual deployments.
