CI/CD Integration Guide

This guide covers automating Dashboards-as-Code workflows in continuous integration and deployment pipelines. It includes complete configurations for GitHub Actions, GitLab CI, Docker-based pipelines, environment promotion, drift detection, and rollback strategies.

GitHub Actions

Complete Workflow

This workflow validates dashboards on every pull request and deploys on merge to main.


# .github/workflows/dashboards.yaml
name: Dashboards-as-Code

on:
  push:
    branches: [main]
    paths: ['src/dashboards/**', 'shared/**']
  pull_request:
    paths: ['src/dashboards/**', 'shared/**']

permissions:
  contents: read
  pull-requests: write

jobs:
  build-and-validate:
    name: Build & Validate
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install osdctl
        run: npm install -g @opensearch-dashboards/cli

      - name: Install project dependencies
        run: npm ci

      - name: Build dashboards
        run: osdctl build -d src/dashboards/ -o yaml

      - name: Validate (schema)
        run: osdctl validate --input-dir ./built

      - name: Lint
        run: osdctl lint --input-dir ./built

      - name: Upload build artifacts
        uses: actions/upload-artifact@v4
        with:
          name: built-dashboards
          path: built/
          retention-days: 7

  diff-on-pr:
    name: Diff (Preview Changes)
    needs: build-and-validate
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install osdctl
        run: npm install -g @opensearch-dashboards/cli

      - name: Download build artifacts
        uses: actions/download-artifact@v4
        with:
          name: built-dashboards
          path: built/

      - name: Diff against staging
        id: diff
        run: |
          osdctl diff --input-dir ./built --profile staging 2>&1 | tee diff-output.txt
        env:
          OSD_URL: ${{ secrets.OSD_STAGING_URL }}
          OSD_TOKEN: ${{ secrets.OSD_STAGING_TOKEN }}

      - name: Post diff as PR comment
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const diff = fs.readFileSync('diff-output.txt', 'utf8');
            const body = `## Dashboard Changes Preview\n\n\`\`\`\n${diff}\n\`\`\`\n\n*Generated by osdctl diff*`;
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: body
            });

  deploy-staging:
    name: Deploy to Staging
    needs: build-and-validate
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install osdctl
        run: npm install -g @opensearch-dashboards/cli

      - name: Download build artifacts
        uses: actions/download-artifact@v4
        with:
          name: built-dashboards
          path: built/

      - name: Validate against staging
        run: osdctl validate --input-dir ./built --server
        env:
          OSD_URL: ${{ secrets.OSD_STAGING_URL }}
          OSD_TOKEN: ${{ secrets.OSD_STAGING_TOKEN }}

      - name: Deploy to staging
        run: osdctl apply --input-dir ./built
        env:
          OSD_URL: ${{ secrets.OSD_STAGING_URL }}
          OSD_TOKEN: ${{ secrets.OSD_STAGING_TOKEN }}

  deploy-production:
    name: Deploy to Production
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install osdctl
        run: npm install -g @opensearch-dashboards/cli

      - name: Download build artifacts
        uses: actions/download-artifact@v4
        with:
          name: built-dashboards
          path: built/

      - name: Validate against production
        run: osdctl validate --input-dir ./built --server
        env:
          OSD_URL: ${{ secrets.OSD_PROD_URL }}
          OSD_TOKEN: ${{ secrets.OSD_PROD_TOKEN }}

      - name: Deploy to production
        run: osdctl apply --input-dir ./built
        env:
          OSD_URL: ${{ secrets.OSD_PROD_URL }}
          OSD_TOKEN: ${{ secrets.OSD_PROD_TOKEN }}

Required GitHub Secrets

Configure these secrets in your repository settings under Settings > Secrets and variables > Actions:

SecretDescription
OSD_STAGING_URLStaging instance URL (e.g., https://dashboards-staging.internal:5601)
OSD_STAGING_TOKENAPI token for the staging instance
OSD_PROD_URLProduction instance URL
OSD_PROD_TOKENAPI token for the production instance

GitHub Environments

For production deployments, configure a GitHub environment named production with:

  • Required reviewers -- At least one team member must approve production deployments.
  • Wait timer -- Optional delay (e.g., 5 minutes) before production deployment starts.
  • Branch protection -- Restrict deployments to the main branch only.

GitLab CI


# .gitlab-ci.yml
stages:
  - build
  - validate
  - diff
  - deploy

variables:
  NODE_VERSION: "20"

.osdctl-setup: &osdctl-setup
  image: node:${NODE_VERSION}
  before_script:
    - npm install -g @opensearch-dashboards/cli
    - npm ci

build:
  <<: *osdctl-setup
  stage: build
  script:
    - osdctl build -d src/dashboards/ -o yaml
  artifacts:
    paths:
      - built/
    expire_in: 1 week

validate:
  <<: *osdctl-setup
  stage: validate
  needs: [build]
  script:
    - osdctl validate --input-dir ./built
    - osdctl lint --input-dir ./built

diff:
  <<: *osdctl-setup
  stage: diff
  needs: [build]
  only:
    - merge_requests
  script:
    - osdctl diff --input-dir ./built
  variables:
    OSD_URL: $OSD_STAGING_URL
    OSD_TOKEN: $OSD_STAGING_TOKEN

deploy_staging:
  <<: *osdctl-setup
  stage: deploy
  needs: [validate]
  only:
    - main
  script:
    - osdctl validate --input-dir ./built --server
    - osdctl apply --input-dir ./built
  variables:
    OSD_URL: $OSD_STAGING_URL
    OSD_TOKEN: $OSD_STAGING_TOKEN
  environment:
    name: staging
    url: $OSD_STAGING_URL

deploy_production:
  <<: *osdctl-setup
  stage: deploy
  needs: [deploy_staging]
  only:
    - main
  when: manual
  script:
    - osdctl validate --input-dir ./built --server
    - osdctl apply --input-dir ./built
  variables:
    OSD_URL: $OSD_PROD_URL
    OSD_TOKEN: $OSD_PROD_TOKEN
  environment:
    name: production
    url: $OSD_PROD_URL

Configure the CI/CD variables in Settings > CI/CD > Variables:

VariableTypeProtectedMasked

OSD_STAGING_TOKENVariableYesYes
OSD_PROD_URLVariableYesNo
OSD_PROD_TOKENVariableYesYes

Build and Deploy Script

Create a reusable shell script that works in any CI environment:


#!/usr/bin/env bash
# scripts/ci-deploy.sh
set -euo pipefail

# Required environment variables:
#   OSD_URL    - Target instance URL
#   OSD_TOKEN  - API authentication token
#   STAGE      - deploy stage: validate, diff, apply

BUILT_DIR="${BUILT_DIR:-./built}"
SRC_DIR="${SRC_DIR:-./src/dashboards}"

case "${STAGE}" in
  build)
    echo "Building dashboards..."
    osdctl build -d "${SRC_DIR}" -o yaml --output-dir "${BUILT_DIR}"
    ;;
  validate)
    echo "Validating dashboards..."
    osdctl validate --input-dir "${BUILT_DIR}"
    osdctl lint --input-dir "${BUILT_DIR}"
    ;;
  diff)
    echo "Diffing against deployed state..."
    osdctl diff --input-dir "${BUILT_DIR}"
    ;;
  apply)
    echo "Applying dashboards..."
    osdctl validate --input-dir "${BUILT_DIR}" --server
    osdctl apply --input-dir "${BUILT_DIR}"
    ;;
  *)
    echo "Unknown stage: ${STAGE}"
    echo "Usage: STAGE=<build|validate|diff|apply> $0"
    exit 1
    ;;
esac

Environment Promotion Pattern

A recommended multi-environment strategy where dashboards are promoted through environments sequentially.

Branch Strategy


feature/add-latency-panel  -->  PR to main
                                   |
main  ------>  Build + Validate  ---->  Deploy to staging (automatic)
                                   |
                                   +--->  Deploy to production (manual approval or tag)

Approach 1: Automatic Promotion

Deploy to staging on every merge to main. Deploy to production after a configurable delay or manual approval (see the GitHub Actions workflow above with the production environment).

Approach 2: Tag-Based Production Deploys

Deploy to staging on merge to main. Deploy to production only when a version tag is pushed:


# Additional job triggered by version tags
deploy-production-on-tag:
  name: Deploy to Production
  if: startsWith(github.ref, 'refs/tags/v')
  runs-on: ubuntu-latest
  environment: production
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: '20'
    - run: npm install -g @opensearch-dashboards/cli
    - run: npm ci
    - run: osdctl build -d src/dashboards/ -o yaml
    - run: osdctl validate --input-dir ./built --server
      env:
        OSD_URL: ${{ secrets.OSD_PROD_URL }}
        OSD_TOKEN: ${{ secrets.OSD_PROD_TOKEN }}
    - run: osdctl apply --input-dir ./built
      env:
        OSD_URL: ${{ secrets.OSD_PROD_URL }}
        OSD_TOKEN: ${{ secrets.OSD_PROD_TOKEN }}

Usage:


git tag v1.2.0
git push origin v1.2.0

Environment-Specific Overrides

If dashboards differ between environments (e.g., different data sources or time ranges), use code to handle the differences:


// src/dashboards/cpu-monitoring.ts
const env = process.env.DEPLOY_ENV || 'dev';

const dataSourceMap: Record<string, string> = {
  dev: 'dev-metrics',
  staging: 'staging-metrics',
  prod: 'prod-metrics-cluster',
};

const dashboard = Dashboard.create('cpu-monitoring')
  .title('CPU Monitoring')
  .labels({ env })
  .addDataSource(
    DataSource.create(dataSourceMap[env]).type('opensearch').default(true)
  )
  // ... panels
  .toYAML(`built/cpu-monitoring.yaml`);

Then set the environment variable in CI:


- name: Build dashboards
  run: osdctl build -d src/dashboards/ -o yaml
  env:
    DEPLOY_ENV: production

Drift Detection

Drift occurs when someone modifies a dashboard through the UI after it was deployed via code. A scheduled CI job detects drift and alerts the team.

GitHub Actions: Scheduled Drift Detection


# .github/workflows/drift-detection.yaml
name: Drift Detection

on:
  schedule:
    # Run every 6 hours
    - cron: '0 */6 * * *'
  workflow_dispatch: {}

jobs:
  detect-drift:
    name: Check for Dashboard Drift
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install osdctl
        run: npm install -g @opensearch-dashboards/cli

      - name: Install dependencies
        run: npm ci

      - name: Build dashboards
        run: osdctl build -d src/dashboards/ -o yaml

      - name: Check for drift
        id: drift
        run: |
          set +e
          osdctl diff --input-dir ./built --output json > drift-report.json 2>&1
          EXIT_CODE=$?
          set -e
          if [ "$EXIT_CODE" -eq 2 ]; then
            echo "drift_detected=true" >> "$GITHUB_OUTPUT"
            # Also generate human-readable report
            osdctl diff --input-dir ./built > drift-report.txt 2>&1 || true
          elif [ "$EXIT_CODE" -eq 0 ]; then
            echo "drift_detected=false" >> "$GITHUB_OUTPUT"
          else
            echo "::error::Drift detection failed with exit code $EXIT_CODE"
            exit 1
          fi
        env:
          OSD_URL: ${{ secrets.OSD_PROD_URL }}
          OSD_TOKEN: ${{ secrets.OSD_PROD_TOKEN }}

      - name: Create issue on drift
        if: steps.drift.outputs.drift_detected == 'true'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const report = fs.readFileSync('drift-report.txt', 'utf8');
            github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: 'Dashboard drift detected in production',
              body: `## Drift Report\n\nThe following dashboards have been modified outside of the DaC workflow:\n\n\`\`\`\n${report}\n\`\`\`\n\n**Action required:** Either update the source code to match the deployed state (\`osdctl pull\`) or re-apply the code to overwrite the manual changes (\`osdctl apply\`).`,
              labels: ['dashboard-drift', 'automated']
            });

Handling Drift

When drift is detected, the team has two options:

  1. Accept the drift -- Pull the deployed state into code and commit it:
    2. 
   osdctl pull --profile prod -o yaml --output-dir ./pulled
   # Review changes, copy into src/dashboards/, commit
  1. Reject the drift -- Re-apply the code to overwrite manual changes:
    2. 
   osdctl apply --profile prod

Rollback Strategies

Strategy 1: Git Revert

The simplest rollback is reverting the Git commit and re-deploying:


# Revert the last commit
git revert HEAD

# Push (triggers CI to deploy the previous state)
git push origin main

Strategy 2: Deploy a Specific Commit

Check out a specific known-good commit and deploy manually:


git checkout <known-good-commit>
osdctl build -d src/dashboards/ -o yaml
osdctl apply --profile prod
git checkout main

Strategy 3: Tag-Based Rollback

If using tag-based production deploys, redeploy from a previous tag:


git checkout v1.1.0
osdctl build -d src/dashboards/ -o yaml
osdctl apply --profile prod
git checkout main

Strategy 4: Pull-and-Fix

If the deployed state is the correct one and the code needs to be updated:


osdctl pull --profile prod -o yaml --output-dir ./pulled
# Copy pulled definitions into your source
cp pulled/*.yaml src/dashboards/
git add .
git commit -m "Sync dashboard code with deployed state"
git push origin main

Best Practices

  1. Always validate before deploying. Run osdctl validate and osdctl lint as mandatory CI steps. Block deployments if they fail.
  1. Use dry-run in CI. Before the actual apply step, run osdctl apply --dry-run to log what would change.
  1. Post diff summaries on PRs. This lets reviewers see the exact impact of dashboard changes before merging.
  1. Use GitHub environments with protection rules. Require manual approval for production deployments.
  1. Set up drift detection. Schedule a periodic job to detect manual changes and alert the team.
  1. Pin the osdctl version in CI. Use a specific version rather than latest to prevent unexpected breakage:
    2. 
   npm install -g @opensearch-dashboards/cli@0.1.0
  1. Store build artifacts. Upload the built/ directory as a CI artifact so the deploy job uses the exact same files that were validated.
  1. Separate build and deploy. The build job should not need server credentials. Only the deploy job needs OSD_URL and OSD_TOKEN.
