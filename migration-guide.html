Migration Guide

This guide covers strategies for adopting Dashboards-as-Code in an organization with existing manually-created dashboards. It covers pulling existing dashboards, converting from ndjson exports, migrating from Grafana, and a recommended gradual adoption strategy.

Overview of Migration Paths

Starting PointMigration Path
Dashboards created in the UIUse osdctl pull to export to YAML/JSON, then manage as code
ndjson exports/backupsUse osdctl convert --from ndjson to convert to the clean format
Grafana dashboardsUse osdctl convert --from grafana to translate Grafana JSON
Starting freshUse osdctl init and write new dashboards in code from the start

Migrating from Manual UI Workflows

Step 1: Pull Existing Dashboards

Use osdctl pull to export all dashboards from a running instance into the clean, version-control-friendly format:


# Pull all dashboards from production
osdctl pull --profile prod -o yaml --output-dir ./pulled

# Or pull only dashboards owned by a specific team
osdctl pull --profile prod --label team=platform -o yaml --output-dir ./pulled

This produces one file per dashboard:


pulled/
  cpu-monitoring.yaml
  memory-overview.yaml
  application-errors.yaml
  network-traffic.yaml

Step 2: Review and Organize

Review the pulled files. Each file follows the clean export format:


apiVersion: dashboard/v1
metadata:
  name: cpu-monitoring
  labels: {}
  annotations: {}
spec:
  title: "CPU Monitoring"
  description: ""
  panels:
    - name: panel-1
      type: visualization
      visualization: line
      gridPosition: { x: 0, y: 0, w: 24, h: 12 }
      query:
        language: DQL
        query: "cpu.usage:*"
  dataSources: []

Common tasks at this stage:

  • Add labels: Add env, team, and other organizational labels.
  • Add descriptions: Fill in empty descriptions.
  • Add annotations: Set owner, source-repo, etc.
  • Rename panels: Replace auto-generated names like panel-1 with descriptive names like cpu-usage-over-time.

Step 3: Set Up the DaC Project

Initialize a project and copy the pulled definitions:


# Create the project
osdctl init --language typescript my-dashboards
cd my-dashboards

# Copy pulled definitions into the source directory
cp ../pulled/*.yaml src/dashboards/

Step 4: Validate and Apply

Validate the pulled definitions, then apply them to mark them as code-managed:


# Validate
osdctl validate --input-dir src/dashboards/

# Apply (this stamps managed-by label without changing the dashboard content)
osdctl apply --input-dir src/dashboards/ --profile prod

After this step, the dashboards are under code management and will show the "Managed by code" badge in the UI.

Step 5 (Optional): Convert to TypeScript SDK

If you want the full power of programmatic dashboard definitions, convert the YAML files to TypeScript SDK code:


// src/dashboards/cpu-monitoring.ts
import { Dashboard, Panel, Query, DataSource } from '@opensearch-dashboards/sdk';

Dashboard.create('cpu-monitoring')
  .title('CPU Monitoring')
  .description('Production CPU metrics across all clusters')
  .labels({ env: 'production', team: 'platform' })
  .annotation('owner', 'platform-team@company.com')
  .timeRange('now-1h', 'now')
  .refreshInterval('30s')
  .addPanel(
    Panel.create('cpu-usage-over-time')
      .visualization('line')
      .gridPosition({ x: 0, y: 0, w: 24, h: 12 })
      .query(Query.dql('cpu.usage:*'))
      .option('showLegend', true)
  )
  .addDataSource(DataSource.create('metrics').type('opensearch').default(true))
  .toYAML('built/cpu-monitoring.yaml');

This conversion is manual but worthwhile for dashboards that benefit from parameterization, reuse, or generation from code.

Converting from ndjson Exports

If your team has existing ndjson exports (from the UI export feature or the _export API), you can convert them to the clean format.

Using osdctl convert


# Convert a single ndjson file
osdctl convert --from ndjson -f exported-dashboards.ndjson -o yaml --output-dir ./converted

# Convert multiple files
osdctl convert --from ndjson -d ./ndjson-backups/ -o yaml --output-dir ./converted

Manual Conversion

If osdctl convert is not yet available, you can process ndjson files manually. An ndjson file contains one JSON object per line:


{"type":"dashboard","id":"cpu-monitoring","attributes":{"title":"CPU Monitoring","panelsJSON":"[{\"panelIndex\":\"1\",\"gridData\":{\"x\":0,\"y\":0,\"w\":24,\"h\":12,\"i\":\"1\"},\"type\":\"visualization\",\"id\":\"cpu-viz\"}]"}}

Key transformations:

  1. Parse panelsJSON: The panelsJSON field in ndjson is a stringified JSON blob. Parse it into an actual JSON array.
  2. Parse optionsJSON: Similarly, optionsJSON is a stringified JSON string.
  3. Remove server-generated fields: Strip _version, updated_at, migrationVersion, and other internal fields.
  4. Add labels and annotations: The ndjson format does not include labels or annotations. Add them manually.
  5. Restructure to clean format: Map the flat attributes into the apiVersion/metadata/spec structure.

Example Node.js script:


// scripts/convert-ndjson.js
const fs = require('fs');
const readline = require('readline');

async function convert(inputFile, outputDir) {
  const fileStream = fs.createReadStream(inputFile);
  const rl = readline.createInterface({ input: fileStream });

  for await (const line of rl) {
    const obj = JSON.parse(line);
    if (obj.type !== 'dashboard') continue;

    const panels = JSON.parse(obj.attributes.panelsJSON || '[]');
    const options = JSON.parse(obj.attributes.optionsJSON || '{}');

    const clean = {
      apiVersion: 'dashboard/v1',
      metadata: {
        name: obj.id,
        labels: { 'managed-by': 'osdctl' },
        annotations: {},
      },
      spec: {
        title: obj.attributes.title,
        description: obj.attributes.description || '',
        panels: panels.map((p, i) => ({
          name: `panel-${i + 1}`,
          type: p.type,
          visualization: 'line',
          gridPosition: {
            x: p.gridData.x,
            y: p.gridData.y,
            w: p.gridData.w,
            h: p.gridData.h,
          },
        })),
        dataSources: [],
        variables: [],
      },
    };

    const outputPath = `${outputDir}/${obj.id}.json`;
    fs.writeFileSync(outputPath, JSON.stringify(clean, null, 2));
    console.log(`Converted: ${outputPath}`);
  }
}

convert(process.argv[2], process.argv[3] || './converted');

Converting from Grafana

If your team is migrating from Grafana to OpenSearch Dashboards, osdctl convert can translate Grafana JSON dashboard definitions.

Using osdctl convert


# Convert a single Grafana dashboard JSON file
osdctl convert --from grafana -f grafana-dashboard.json -o yaml --output-dir ./converted

# Convert a directory of Grafana exports
osdctl convert --from grafana -d ./grafana-exports/ -o yaml --output-dir ./converted

What Gets Converted

Grafana FeatureOpenSearch DaC Equivalent
Dashboard title, descriptionspec.title, spec.description
Panel layout (gridPos)panels[].gridPosition
Panel types (graph, stat, table, gauge, heatmap, text)Mapped to line, metric, table, gauge, heatmap, markdown
Time rangespec.timeRange
Refresh intervalspec.refreshInterval
Template variablesspec.variables
Data source referencesspec.dataSources

What Requires Manual Adjustment

Grafana FeatureAction Required
PromQL queriesRewrite as PPL, DQL, SQL, or Lucene queries targeting your OpenSearch indices
LogQL queriesRewrite as PPL or DQL queries
Grafana-specific panel optionsMap to OpenSearch visualization options
Transformations (reduce, organize, filter)Implement in the query language or remove
Grafana alerting rulesNot converted; handle separately
Dashboard linksManual recreation

Migration Workflow

  1. Export the Grafana dashboard as JSON (Settings > JSON Model in Grafana UI).
  2. Run the conversion: osdctl convert --from grafana -f dashboard.json -o yaml.
  3. Review the output and rewrite PromQL/LogQL queries as PPL or DQL.
  4. Validate: osdctl validate --input-dir ./converted.
  5. Deploy: osdctl apply --input-dir ./converted --profile dev.
  6. Test the dashboard in the UI and adjust as needed.
  7. Once verified, commit to Git.

Gradual Adoption Strategy

For organizations with many existing dashboards, a gradual migration is recommended over a "big bang" approach.

Phase 1: New Dashboards Only

Start by writing all new dashboards as code. Leave existing dashboards untouched.


Existing dashboards:  UI-managed (unchanged)
New dashboards:       Code-managed via osdctl

This lets the team learn the DaC workflow without risk to existing dashboards.

Timeline: 2-4 weeks

Phase 2: High-Value Dashboards

Identify the most critical dashboards (the ones that break most often, are shared across teams, or need to be consistent across environments) and migrate them to code.


# Pull the high-value dashboards
osdctl pull --profile prod --label team=platform -o yaml

# Review, add labels, commit to Git
# Set up CI/CD for these dashboards

Timeline: 2-4 weeks

Phase 3: Team-by-Team Rollout

Migrate team by team. Each team pulls their dashboards, adds labels, and sets up their CI/CD pipeline.

Use labels to track migration progress:

LabelMeaning
managed-by: osdctlDashboard is code-managed
(no label)Dashboard is still UI-managed

Monitor progress:


# Count code-managed dashboards
osdctl pull --profile prod --label managed-by=osdctl | wc -l

# Count all dashboards
osdctl pull --profile prod | wc -l

Timeline: 4-8 weeks

Phase 4: Full Adoption

Once all teams have migrated, establish the organizational policy:

  • All new dashboards must be created as code.
  • UI-only dashboards show a notice encouraging migration.
  • Drift detection runs on all code-managed dashboards.

Handling the managed-by Label

The managed-by: osdctl label is the key mechanism for tracking which dashboards are code-managed.

What It Does

  • UI indicator: Dashboards with this label show a "Managed by code" badge in the listing and detail views.
  • Warning on edit: The UI shows a tooltip: "Edits may be overwritten by the next code deployment."
  • Drift detection: osdctl diff uses the last-applied-hash annotation (set alongside managed-by) to detect manual changes.
  • Filtering: osdctl pull --label managed-by=osdctl pulls only code-managed dashboards.

When It Gets Set

The label is automatically applied by osdctl apply. You do not need to set it manually in your dashboard definitions (though you can).

Removing Code Management

To stop managing a dashboard as code and return it to manual UI management:

  1. Remove the dashboard source file from your repository.
  2. Manually remove the label via the API:

curl -u admin:admin \
  -X PUT "http://localhost:5601/api/saved_objects/dashboard/cpu-monitoring" \
  -H 'Content-Type: application/json' \
  -H 'osd-xsrf: true' \
  -d '{
    "attributes": { ... },
    "labels": {
      "env": "production",
      "team": "platform"
    }
  }'

Or use osdctl to update the labels (removing managed-by).

Emergency Manual Edits

The managed-by label does not prevent manual edits. Users can still modify code-managed dashboards through the UI for emergency changes. When osdctl diff runs next, it will report the drift, and the team can decide whether to incorporate the change into code or overwrite it.

Troubleshooting

"Dashboard already exists" on first apply

If you pull a dashboard and immediately apply it back, osdctl apply will report it as UNCHANGED (not an error). If you see a conflict error, it may be a version mismatch. Use --dry-run first to check.

Pulled YAML does not match original exactly

The clean export format restructures the data for readability. The deployed dashboard is functionally identical even if the YAML representation differs from what you might hand-write.

Labels not appearing after pull

If your existing dashboards were created before the DaC feature was available, they will not have labels. Add labels manually after pulling, then apply to persist them.

Grafana conversion produces incomplete dashboards

The Grafana converter handles structural conversion but cannot translate PromQL/LogQL queries to PPL/DQL. These must be rewritten manually. Check the validation output for panels with missing or invalid queries.
